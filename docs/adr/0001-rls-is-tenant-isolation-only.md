# 0001. RLS にはテナント分離だけを持たせる

**状態**: 採用

## 背景

Postgres の RLS はロール別の細かな権限制御も書ける。`memberships` を引いて
`role = 'admin'` を条件に入れれば、DB レベルで「admin だけ削除できる」も表現できる。

## 決定

**RLS のポリシーは `org_id = current_org_id()` の単純チェックのみ**とする。
ロール × リソース × 操作の制御は Service Layer（TypeScript）に置く。

## 理由

- **壊れたときに気付けるかが違う。** SQL のポリシーは条件を間違えても
  エラーにならず、静かに「見えるべきものが見えない」か「見えてはいけないものが見える」
  になる。TypeScript 側なら型とユニットテストで捕まえられる
- **テストのしやすさ。** 認可マトリクスをユニットテストで網羅するのは容易だが、
  同じ網羅を RLS でやるには実 DB とロール別セッションが要る
- **二重防御として機能させるには、両者が独立していた方がよい。** 同じ複雑な
  条件を2箇所に書くと、同じ考え違いを2箇所でするだけになる。RLS は
  「テナントを跨がない」ことだけを保証し、Service Layer が漏れたときの
  最後の砦になる

## 捨てたもの

RLS だけで全ての認可を表現する案。Service Layer のバグでテナント内の
権限違反が通る余地は残るが、**テナントを跨ぐ流出だけは RLS が必ず止める**。
守るべき優先順位に対して、この分担が最も費用対効果が高いと判断した。
