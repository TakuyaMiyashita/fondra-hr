# 0007. 検証環境ではメール確認を有効化しない

**状態**: 採用

## 背景

`auth.email.enable_confirmations` は無効のままになっている。無効の間は
**他人のメールアドレスでも登録できる**ため、[デプロイ手順](../deployment.md)
では「本番として運用するなら有効化が要る設定」として挙げていた。

実装側は [0006](./0006-defer-org-creation-until-email-confirmed.md) で対応済みで、
リダイレクト許可リストも整備してある（PR #25）。つまり**トグルを倒すだけ**の
状態が続いていた。

## 決定

**検証環境では有効化しない。** `supabase/config.toml` もホスティング先の
Supabase プロジェクトも `enable_confirmations = false` のままとする。

## 理由

有効化するには、組み込みのメール送信では足りずカスタム SMTP が要る。
そして**このプロジェクトの構成ではカスタム SMTP を実用的に組めない。**

- **組み込みメールは 2通/時**。サインアップ・招待・マジックリンク・
  パスワードリセットで共有する。「サインアップを1回試して招待も試す」で
  上限に達する。Supabase 自身も配信 SLA なしの非本番用と位置づけている
- カスタム SMTP を入れれば 30通/時に上がる。Vercel Marketplace の
  `messaging` カテゴリで提供されるのは Resend の1件
- **Resend のテスト用ドメインは、自分のアカウントのメールアドレス宛にしか
  送れない。** 任意の宛先に送るには独自ドメインの検証が要る
- アプリは `fondra-hr-staging.vercel.app` にあり、**`vercel.app` の DNS は
  管理下にないため検証できない**。独自ドメインの取得が前提になる

得られるもの（実ユーザーの居ない環境で、他人のアドレスでの登録を防ぐ）に対して、
独自ドメインの取得・DNS 設定・SMTP 運用は釣り合わない。
[0005](./0005-single-environment.md) と同じく、**実ユーザーが居ないことから
導かれる判断**である。

## 捨てた案

| 案                                   | 却下理由                                                 |
| ------------------------------------ | -------------------------------------------------------- |
| 組み込みメールのまま有効化する       | 2通/時では検証が成立しない。招待フローを一度試すと詰まる |
| Resend + テスト用ドメイン            | 自分のアドレス宛しか送れず、招待フローを実演できない     |
| 独自ドメインを取得して Resend で検証 | 動くが、ドメイン代と DNS 運用に見合う利点が無い          |

## 影響

- **実ユーザーを受け入れる段階になったら、この ADR を新しい ADR で上書きする。**
  そのときは独自ドメインの取得が前提になる
- `supabase/config.toml` を `false` のまま保つ理由がもう一つ増えた。
  ローカル開発と e2e はサインアップから画面表示までを一続きで通すため、
  確認メールを挟むとテストが成立しない
- 実装（`completePendingSignUp`）は**有効・無効のどちらでも動く**ままにしておく。
  有効化が判断ひとつで済む状態を保つため、実装を巻き戻さない
