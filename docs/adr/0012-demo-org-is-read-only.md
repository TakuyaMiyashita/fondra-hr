# 0012. 公開デモの組織は閲覧専用にする

**状態**: 採用

## 背景

README は公開デモ（<https://fondra-hr-staging.vercel.app>）の資格情報を載せている。
owner を含む全ロールのメールアドレスとパスワード（`demo-password123`）が書いてある。

認可の効き方をロールごとに見せることがデモの主目的なので、これ自体は意図的だった。
「同じ画面を member で開くと生年月日が『—』になる」「他人の 1on1 が一覧から消える」
——文章で説明するより、実際に触ってもらう方が早い。

問題は、**owner の資格情報が公開されている以上、誰でも壊せる**こと。

- 従業員を全件削除できる
- 組織名を書き換えられる（公開ページに出る）
- 他メンバーのロールを変更できる
- 招待を発行できる

README にも「書き込みも削除もできる。データが荒れていたら作り直している最中かも
しれない」と書いてあった。認可の設計を見せることが売りのプロジェクトで、
そのデモが荒れているのは筋が悪い。

## 決定

**デモ組織に対する書き込みだけを Service Layer で拒否する。**
ログインは4ロールとも開けたままにする。

`authorize()`（`src/services/authorize.ts`）に判定を1つ足す。全ドメイン書き込みが
必ず通る唯一の関門なので、ここだけで済む。

```
DEMO_READONLY_ORG_ID が設定されていて
  かつ ctx.orgId がその組織
  かつ action が create / update / delete
→ DemoReadOnlyError
```

環境変数が未設定なら何も起きない。ローカル開発・CI・テストは素通りする。
検証環境にだけデモ組織の UUID を設定する。

対象を**組織で絞る**のが要。サインアップして自分の組織を作った人は、そちらには
自由に書ける。凍るのはデモ組織だけ。`createOrganizationWithOwner` と
`acceptInvitation` は `authorize()` を通らないブートストラップ関数なので、
サインアップと招待受諾は引き続き動く。

**エラーは `AuthorizationError` と区別する。** owner でログインした人が
「権限がありません」と言われると、認可が壊れているように見えてデモの趣旨と
正反対になる。`DemoReadOnlyError` を継承クラスとして足し、
`authorizationMessage()` で文言を出し分ける。継承にしているのは、
Server Action 側の `catch (e instanceof AuthorizationError)` をそのまま
効かせるため。

## 理由

- **デモの一番の見せ場は読み取り側にある。** ロール別の可視性・フィールドの
  マスク・当事者限定の絞り込みは、どれも「何が見えるか」の話。書き込みを
  止めてもデモの価値は落ちない
- **止める場所が1つで済む。** `authorize()` は全書き込みの関門として既にある。
  新しい機能を足す人が「デモ対応」を思い出す必要がない
- **書き込みを試したい人にはローカルがある。** README の「動かす」に
  `npx supabase db reset` の手順があり、デモと同じデータが入る

## 捨てたもの

**viewer の資格情報だけ公開する案。** 最も単純だが、ロールごとの見え方の違いを
見せられなくなる。それはデモの存在理由そのものなので採らない。

**viewer アカウントを足すだけの案。** 「見るだけの人用」の入口はできるが、
owner の資格情報が公開されたままなので何も守られない。

**定期的に seed をやり直す案。** 荒らされても自動で戻る。ただし**荒れている
時間帯が必ず存在する**し、たまたまその時に見た人には伝わらない。

**DB のトリガーで止める案。** プロダクトコードにデモ都合を持ち込まずに済む。
ただし生の Postgres エラーが上がってきて UI 側で扱えず、
「権限がありません」より分かりにくい表示になる。

## 影響

プロダクトコードにデモ都合の分岐が1つ入る。これは意図的なトレードオフで、
代わりに「デモが荒らされない」ことと「拒否理由が利用者に伝わる」ことを得ている。
分岐は環境変数で切られており、本番として運用する場合は設定しなければよい。
