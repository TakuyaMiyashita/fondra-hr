# 0013. 死活監視は GitHub Actions の cron に置き、失敗を Issue にする

**状態**: 採用

## 背景

`/api/health` は認証不要で DB 到達性まで返す
（`src/app/api/health/route.ts`）。[デプロイ手順](../deployment.md) には
`curl` で手で叩く手順があるが、**定期的に叩く仕組みが無かった**。

手で叩く手順しか無いということは、実際には誰も叩かないということでもある。
デプロイ直後に一度確認して以降、検証環境が落ちても気付く経路が無い。
このプロジェクトの場合、README がデモ環境をトップに掲げているため、
「リンクを踏んだ人だけが気付いている」状態になる。

一方で [ADR 0005](./0005-single-environment.md) のとおり、ここは実ユーザーを
持たない検証環境ひとつである。SLA も当番も無い。監視に本番相当の作りを
持ち込むと、得るもののない複雑さを抱えることになる。

## 決定

**GitHub Actions の `schedule` から30分おきに `/api/health` を叩く。**
3回連続で健全な応答が返らなければジョブを失敗させ、あわせて
`health-check` ラベルの Issue を1件だけ起票する。復旧を検知したら
その Issue を自動でクローズする。

- ワークフロー: `.github/workflows/health-check.yml`
- 判定は HTTP ステータスと**本文の両方**を見る
- 対象 URL は既定値を直書きし、リポジトリ変数 `HEALTH_CHECK_URL` で上書きできる

## 理由

### なぜアプリの外側なのか

**監視対象と同じ場所で動く監視は、対象が落ちたときに一緒に止まる。**
アプリが起動しない・デプロイが壊れている・Vercel 側の障害、といった
一番知りたい状況でこそ動かなくなる。GitHub Actions は Vercel とも
Supabase とも別系統なので、両方が落ちても実行され、結果を残せる。

### なぜ本文まで見るのか

ステータスコードだけでは次を見逃す。

- **307**: `PUBLIC_PATHS` から `/api/health` が外れると、認証必須になり
  `/login` へリダイレクトされる。監視が「エンドポイントの公開」ごと守る
- **200 + HTML**: 監視先が別プロジェクトや停止済みデプロイを指していると、
  200 でアプリと無関係な HTML が返ることがある

`"status":"ok"` と `"database":"ok"` の両方を確認して初めて
「このアプリが DB まで到達できている」と言える。

### なぜ3回リトライするのか

サーバーレスのコールドスタート、Vercel 側の瞬間的な 5xx、DNS の揺れで
1回失敗することはある。それで毎回 Issue が立つと、**「どうせ誤報」に
なって誰も見なくなる**。監視は落ちたことを伝えられなければ意味が無いが、
誤報で信頼を失えば同じく意味が無い。30秒間隔で3回試す。

### なぜ Issue まで作るのか

スケジュール実行の失敗通知（メール）は **cron を最後に編集した人にしか
届かない**うえ、他の通知に埋もれる。Issue にしておけば、

- リポジトリを開いた時点で目に入る
- 落ちた時刻・応答・実行ログへのリンクが残り、後から追える
- 復旧で自動クローズするので、**「開いている Issue = 今落ちている」**が成り立つ

起票は1件に集約する（開いている Issue があれば作らない）。30分おきに
立て続けると通知が飽和し、本当に見るべき1件目まで無視されるようになる。

### なぜ30分間隔なのか

実ユーザーが居らず、通知を受けても即応する当番も居ない。間隔を詰めて
縮むのは「誰も見ていない時間帯の検知遅れ」だけで、対価として Actions の
実行回数と通知のノイズが増える。ADR 0005 の「環境を分けても得るものが無い」
と同じ理由で、ここも詰めない。

cron は `11,41 * * * *` としている。`:00` ちょうどは GitHub 全体で実行が
集中し、遅延しやすいため。

### なぜ URL を直書きし、かつ変数でも上書きできるのか

この URL は **README がデモ環境として公開しているもの**であり、秘密情報では
ない。隠す実益が無いのに変数必須にすると、変数を設定するまで監視が黙って
何もしない状態が生まれる（監視として最悪の失敗の仕方をする）。

一方でデプロイ先を差し替えたときにコミットを要求するのも筋が悪いので、
`vars.HEALTH_CHECK_URL` があればそちらを優先する。**未設定でも動く**のが要点。

## 捨てた案

### Vercel Cron（`vercel.json` の `crons`）

**監視対象の中で動くため却下。** デプロイが壊れていれば cron も動かず、
一番知りたい障害を検知できない。加えて Hobby プランの cron は1日1回・
実行時刻は時間単位の精度しか無く、通知先も別途用意する必要がある。

### 外形監視 SaaS（UptimeRobot / Better Stack / Checkly 等）

**製品としてはこちらが上**。複数リージョンからの監視、1分間隔、
ステータスページ、電話・Slack への通知まで揃っている。それでも採らない。

- 設定がリポジトリの外にあり、**PR でレビューできない**。
  このリポジトリは「判断が差分として残る」ことを重視している
- アカウントと外部サービスへの依存が増える。検証環境ひとつのために
  払うコストとして重い
- 実ユーザーを受け入れる段になったら、そのときはこちらへ移す。
  ADR 0005 が「本番運用に切り替えるなら」を併記しているのと同じ扱い

### Slack / メール / Discord への Webhook 通知

**Secret と外部アカウントが要るわりに、得るものが Issue と重複する**ため却下。
GitHub は失敗したジョブについて通知を送るし、Issue はリポジトリ上に残る。
受け取り口を増やすより、確実に残る場所が1つあるほうがよい。

### README への監視バッジ

ワークフローのバッジを README に貼れば状態が一目で分かるが、
**Supabase 無料枠の一時停止などで赤くなったバッジが、ポートフォリオの
トップに出続ける**。持ち主はメールと Issue で既に気付けるので、
バッジが増やすのは通知経路ではなく見栄えの悪さだけになる。

### 死活の履歴を DB やファイルに蓄積する

稼働率を出したくなるが、そのためのテーブルやコミットは監視対象そのものを
汚す。Actions の実行履歴が既に「いつ失敗したか」を保持している。

## 影響

### GitHub Actions の cron は正確でも確実でもない

- **遅延する。** 混雑時は数分〜十数分ずれる。指定は最速で5分間隔だが、
  短くしても実際にその間隔で回る保証は無い
- **スキップされることがある。** 高負荷時に実行が落とされる
- **60日間リポジトリに活動が無いと自動で無効化される。**
  ポートフォリオは放置されうるので、これは現実的なリスク。無効化の前に
  GitHub から所有者へ通知が届くので、そこで再有効化する

そのため、この監視は「N分以内に検知する」ことを約束しない。**落ちたまま
放置されている状態に気付ける**ための仕組みとして扱う。厳密な検知時間が
要るなら、上で捨てた外形監視 SaaS に移すのが筋。

### 定期的に叩くこと自体が副作用を持つ

`/api/health` は DB に触れるため、30分おきの実行は Supabase から見て
「活動」になる。無料枠プロジェクトの一時停止（一定期間アクセスが無いと
停止する）を、この監視が結果的に防ぐ。**望ましい副作用だが、監視が観測対象を
変えている**ことは認識しておく。これに依存し始めると、監視を止めた瞬間に
デモ環境が停止する。

### 権限

リポジトリ既定の `GITHUB_TOKEN` は read のみ。ワークフロー側で
`issues: write` を明示している。これはワークフロー単位の宣言で、
リポジトリ設定の既定値を上書きする。
