# 0014. コントラストは実テキストを走査して測る（0010 の検証手段を具体化）

**状態**: 採用

**関連**: [0010](./0010-color-contrast-is-in-scope.md) の「配色のコントラストも担保する」を
実際に担保できる形にする

## 背景

0010 は配色をスコープに入れ、`tests/e2e/a11y-contrast.spec.ts` で検証すると決めた。
だがその検査は**トークンを1つずつ、決め打ちの背景に対して**測るものだった。

```
--muted-foreground を --background の上で測る   → 4.73:1 合格
--muted-foreground を --card の上で測る         → 4.73:1 合格
```

**測っていない組み合わせは通ってしまう。** 実際に走査したところ、
light テーマで2件の違反が見つかった。どちらも 0010 の時点から存在していた。

| 箇所                                   | 前景 / 背景                              | 実測       | 必要 |
| -------------------------------------- | ---------------------------------------- | ---------- | ---- |
| アバターのイニシャル（全画面ヘッダー） | `text-muted-foreground` / `bg-muted`     | **4.35:1** | 4.5  |
| `Badge variant="destructive"`          | `text-destructive` / `bg-destructive/10` | **3.97:1** | 4.5  |

`--muted-foreground` は `--background`（白）の上でしか測っておらず、
`--muted`（`oklch(0.97)`）の上に載る組み合わせが存在することに気づいていなかった。

axe の `color-contrast` はこれを標準ルールとして持っているが、
**`lab()` を誤読して false positive を出すため使えない**（0010 の「影響」を参照）。

## 決定

**描かれているテキストをそのまま走査して測る。**

- 直接の子に空白でないテキストを持つ要素を全て集め、
  文字色と**祖先を遡って合成した背景**を canvas に描いて比べる
- WCAG の「大きな文字」（24px 以上、または 18.66px 以上の太字）は 3:1、
  それ以外は 4.5:1
- 対象ページは `a11y-axe.spec.ts` と揃え、**ダイアログを開いた状態**も見る
- light / dark の両方で回す

あわせて、見つかった2件を**トークン側で**直す。

- `--muted-foreground` を light で `0.556` → `0.54`（`--muted` の上で 4.62:1）
- `--destructive` を light で `0.577` → `0.51`（バッジの上で 4.80:1）

## 理由

### なぜトークンを直すのか（コンポーネントではなく）

`badge.tsx` は `src/components/ui/` にあり、「shadcn 自動生成・手動編集しない」方針。
触ると `shadcn add` のたびに差分が戻る。0010 が `ring-ring/50` で同じ制約に
当たったときと同じ判断をする。

`--destructive` を暗くすると、`bg-destructive` の上の白文字も 4.77:1 → 5.79:1 に
改善する。片方を直すともう片方が悪化する関係にはなっていない。

### なぜ「最初に見つかった不透明な背景」で止めないのか

半透明の背景はその下の色と混ざって見える。`bg-destructive/10` はまさにそれで、
外側から順に重ねないと実際の色にならない。祖先を根まで遡ってレイヤーを集め、
外側から canvas に重ねる。

### なぜ測る前にトランジションを止めるのか

shadcn のテーブル行などは `transition-colors` を持つ。テーマを切り替えた直後の
`getComputedStyle` は**遷移途中の中間色**を返すため、切替前の文字色と切替後の
背景を突き合わせることになり、**実際には起きない組み合わせを違反として報告する**。
最初の実装ではこれで dark の全ページが落ちた。

### なぜ `light` クラスを外すのか

next-themes は `light` / `dark` を付け替える。`dark` を足すだけだと両方付いた
状態になり、実際のアプリでは起きない。

## 捨てた案

| 案                                         | 却下理由                                                     |
| ------------------------------------------ | ------------------------------------------------------------ |
| axe の `color-contrast` を有効化する       | `lab()` を誤読して false positive を出す（0010 の「影響」）  |
| `badge.tsx` / `avatar.tsx` を直接編集      | `shadcn add` のたびに差分が戻る。規約違反                    |
| トークン単位の検査に組み合わせを足していく | 組み合わせの列挙が漏れる。漏れたことに気づく手段が無い       |
| 違反した箇所だけ個別に上書きクラスを足す   | 同じトークンを使う他の箇所が落ちたままになる。原因が散らばる |

## 影響

トークン単位の検査（チャート系列色・フォーカスリング）は**残す**。
非テキストは走査対象に文字が無いため、実テキスト走査では拾えない。

`--muted-foreground` は白背景でも 4.73:1 → 5.06:1 になり、余裕が増えた。
`--destructive` は light だけを変え、dark（`oklch(0.704 0.191 22.216)`）は
そのままで合格している。
