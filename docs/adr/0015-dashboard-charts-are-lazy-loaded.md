# 0015. ダッシュボードのグラフは遅延読み込みする（総バイト数は増えるが採用する）

**状態**: 採用

## 背景

`/dashboard` のルート固有 JS 377 KB のほぼ全てが Recharts である
（[テスト方針](../testing.md)の「バンドルサイズの見方」）。

一方でダッシュボードの主役はグラフだけではない。統計カード4枚と
最近のアクティビティ一覧は、Recharts が1バイトも届かなくても描ける。
同じ塊に入れている限り、**グラフ以外まで Recharts のダウンロードを待つ**。

## 決定

**グラフのコンポーネントを `dashboard-charts.tsx` に分け、
`next/dynamic`（`ssr: false`）で読む。**

- 空状態の分岐は**呼び出し側**（`dashboard-client.tsx`）に置く
- 読み込み中は 300px の Skeleton を出す

## 理由

### 総バイト数は増える。それでも採用する

ここが直感に反するので明記する。

| 指標                                           | 前      | 後          |
| ---------------------------------------------- | ------- | ----------- |
| `/dashboard` のルート固有 JS                   | 372 KB  | **377 KB**  |
| 統計カードが読めるまで（Fast 3G, 3回の中央値） | 3138 ms | **2083 ms** |

**`next/dynamic` は総量を減らさない。後ろにずらすだけである。** 分割の分だけ
むしろ 5 KB 増えている。バイト数の表だけを見ると「効果が無い」に見えるが、
**意味のある最初の表示までは 1 秒速くなっている**。

判断の基準は総バイト数ではなく、ユーザーが最初に何かを読めるまでの時間とする。

### なぜ `ssr: false` なのか

`ResponsiveContainer` は実際の描画領域の寸法に依存しており、サーバー側では
確定しない。SSR しても捨てる HTML が増えるだけになる。

### なぜ空状態の分岐を呼び出し側に置くのか

チャート側に置くと、**データが0件の組織でも「データがありません」を出すためだけに
Recharts を取りに行く**。呼び出し側で分岐すれば、空の組織では chunk 自体が
発行されない。

## 捨てた案

| 案                                          | 却下理由                                                           |
| ------------------------------------------- | ------------------------------------------------------------------ |
| そのまま静的 import で置いておく            | グラフ以外の内容まで Recharts の到着を待つ。3G で1秒の差           |
| Recharts をやめて軽いグラフ実装に置き換える | 変更範囲が大きく、a11y（系列色のコントラスト）を作り直すことになる |
| `ssr: true` で遅延だけかける                | `ResponsiveContainer` が寸法を決められず、捨てる HTML が増えるだけ |
| 空状態の分岐もチャート側に置く              | 空の組織でも Recharts を取りに行く                                 |

## 影響

`scripts/measure-bundle.mjs --throttle` が計測手段。**localhost では帯域制約が
無いため、絞らないとこの差は時間に現れない**（どちらも 150ms 前後になる）。

「JS が何 KB 読み込まれた時点か」では測れない。サイドバーの prefetch が競合し、
同じビルドでも 113〜330 KB と3倍近く振れる。

`tests/e2e/dashboard-charts.spec.ts` が回帰を止める。データがある組織では
svg と系列が描かれること、**データが無い組織では svg が描かれないこと**の
両方を見ている。
