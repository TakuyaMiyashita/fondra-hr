# 0016. 記録の残る従業員は削除させず、匿名化で応える

**状態**: 採用

## 背景

`employees` を参照する外部キーが4本とも `on delete cascade` で、Service Layer の
`deleteEmployee` にも関連チェックが無かった。**従業員を1人消すと、その人が
「評価者として書いた他人の評価」と「面談者として実施した部下の 1on1」まで
黙って消えていた。**

ローカルのデモデータで実測した（評価者として最多の従業員を1人削除）。

| 対象                                   | 削除前    | 削除後 |
| -------------------------------------- | --------- | ------ |
| 評価者として**他人について**書いた評価 | 20件      | 0件    |
| 面談者として実施した 1on1              | 38件      | 0件    |
| 本人が受けた評価 / 1on1                | 2件 / 5件 | 0件    |

`DELETE 1` の裏で65件が消える。退職した上長を消すと、**その人が書いた部下全員の
評価が、部下側の履歴から欠落する。** 監査ログには氏名しか残らないため、
内容は復元できない。

一貫性としても浮いていた。`deleteDepartment` は子部署・所属従業員があれば拒否し、
`deleteSkill` は割当済みなら拒否する。**`employees` だけが素通しだった。**

## 決定

**評価・1on1 が紐づいた従業員は削除させない。**

- 外部キーを `on delete restrict` に変更（`evaluations` の被評価者・評価者、
  `one_on_ones` の対象者・面談者）
- `deleteEmployee` が件数を数え、件数入りのメッセージで拒否する
- 退職者は `status = 'retired'` に倒す運用にする

**個人情報の削除請求には「匿名化」で応える**（`anonymizeEmployee`）。
レコードは残したまま、氏名・カナ・メール・生年月日・アバター・社員番号・
ログインユーザーとの紐付けを落とし、ステータスを退職にする。

## 理由

### なぜ削除を止めるだけで終わらせないのか

止めるだけだと、個人情報の削除請求に応える手段が無くなる。**「消せない」と
「消さなくてよい」は別**なので、受け皿を同時に用意する。

### なぜ `employee_skills` は cascade のままなのか

スキル割当はその従業員自身の属性でしかなく、消えても**他人の記録は損なわれない**。
止める理由が無い。

### なぜ社員番号も置き換えるのか

他システムとの突き合わせキーになり得る。NOT NULL かつ組織内で一意なので、
id から決まる `ANON-<id の先頭8文字>` を入れて衝突を避ける。

### なぜ `user_id` を落とすのか

紐付けが残ると、**本人限定の閲覧範囲がアカウント側から生き続ける**
（`getOneOnOneScope` / `canReadEvaluationDetail`）。匿名化したのに本人として
1on1 や評価が見えるのでは意味が無い。

### なぜアバターの削除を DB 更新より先にやるのか

順序を逆にすると、Storage の削除に失敗したときに**「匿名化済みなのに顔写真は
残っている」**状態になる。先に消しておけば、失敗しても匿名化されていない
状態で止まる。Storage は Service Layer の外なので、権限は手前で確かめる
（`assertCanUpdateAvatar`。アップロードと同じ作法）。

拡張子は登録時のファイル名で決まるため、パスを組み立てずにフォルダごと
列挙して消す。差し替えの残骸も一緒に落ちる。

### なぜ監査ログに旧氏名を残さないのか

何を消したかの記録に個人情報を戻しては意味が無い。消した事実と対象 id だけを残す。

## 捨てた案

| 案                                         | 却下理由                                                                       |
| ------------------------------------------ | ------------------------------------------------------------------------------ |
| cascade のまま Service Layer だけで止める  | Service Layer を通らない経路（service_role・将来の別サービス）で消える         |
| 従業員を論理削除（`deleted_at`）にする     | 全クエリに条件が増え、消し忘れると他テナントではなく他社員のデータが漏れる     |
| 匿名化で 1on1 のメモ・評価コメントも消す   | 他人が書いた記録であり、自動で消すと評価履歴そのものが壊れる（下記の積み残し） |
| 削除時に関連レコードを別テーブルへ退避する | 退避先を誰も読まない。読まれないバックアップは無いのと同じ                     |

## 影響

`tests/rls/domain-tables.test.ts` が**外部キー側でも止まること**を直接確かめる。
Service Layer のガードを外しても DB で止まる。

## 積み残し

**1on1 のメモと評価コメントの本文は匿名化の対象外。** 本文に個人情報が
書かれている場合は個別に編集する必要がある。自動で消すと他人が書いた評価履歴が
壊れるため、意図的に手を付けていない。ダイアログにもその旨を明記している。

厳密な削除請求対応には、本文を対象にした個別の仕組み（該当箇所の指摘と
編集の導線）が要る。
