# 0017. 死活監視の定期実行をやめる（0013 の cron 判断を上書き）

**状態**: 採用

**上書き対象**: [0013](./0013-health-check-runs-on-github-actions.md) の
「GitHub Actions の `schedule` から30分おきに叩き、失敗を Issue にする」

## 背景

0013 で死活監視を入れた。**2週間動かして、前提が3つとも崩れた。**

### 1. 監視対象は「眠るように作られている」

検証環境は Supabase の無料枠にあり、**7日間使われないと自動で一時停止する**。
実測でもそうなった。

| できごと               | 日時             |
| ---------------------- | ---------------- |
| 最後に人が触った       | 2026-08-28       |
| 死活確認が失敗し始めた | 2026-09-02 21:57 |
| 通知が鳴り続けた期間   | 以後9日間で66回  |

このとき `/api/health` は `503 {"status":"error","database":"error"}` を返しており、
**監視は正しく動いていた**。アプリは 200 を返し、DB だけが落ちている状態を
設計どおり検出していた。

問題は検出の精度ではなく、**検出した事象が異常ではなかった**こと。
[ADR 0005](./0005-single-environment.md) のとおりここは実ユーザーを持たない
検証環境で、使われない期間があるのは正常な状態である。
眠るように作られた環境を常時監視すると、出てくるのは異常ではなく
「今日も眠っている」という通知になる。

### 2. 監視の DB アクセスでは一時停止を防げない

停止までの7日間、死活確認は止まらず DB に `select 1` を投げ続けていた。
**それでも一時停止した。** 監視自体をキープアライブ代わりにする案は使えない。

### 3. cron は要求した間隔で回らない

`11,41 * * * *`（30分おき）と書いたが、実際に届いたのは**3〜5時間に1回**だった。

| 期間             | 実行回数 | 平均間隔       |
| ---------------- | -------- | -------------- |
| 成功していた期間 | 33回     | **276分**に1回 |
| 失敗していた期間 | 66回     | **203分**に1回 |

無料の GitHub Actions では `schedule` が大きく間引かれる。0013 は「30分おき」を
前提に検知の遅れを見積もっていたが、その前提自体が成り立っていなかった。

## 決定

**定期実行をやめ、`workflow_dispatch`（手動）とデプロイ後の確認に絞る。**

- `schedule` を外す
- ラベル作成・Issue 起票・Issue 自動クローズを**削除する**

## 理由

### なぜ Issue の仕組みごと消すのか

あれは「誰も見ていない時間に落ちたことを後から知る」ための仕組みで、
**定期実行が前提**だった。手で叩く運用では、結果は叩いた本人がその場で見る。
「開いている Issue = 今落ちている」という 0013 の不変条件も、定期実行が
無ければ成り立たない。動かない前提の上に立つ仕組みを残すと、
次に読む人が「監視されている」と誤読する。

### なぜワークフロー自体は残すのか

プローブの中身（HTTP ステータスと**本文の両方**を見る。307 リダイレクトや
200 + HTML を弾く）はデプロイ後の確認として価値がある。
`docs/deployment.md` の `curl` 手順より厳密なので、手で叩ける形で残す。

## 捨てた案

| 案                               | 却下理由                                                                  |
| -------------------------------- | ------------------------------------------------------------------------- |
| cron の間隔を空けて通知を減らす  | 頻度の問題ではない。眠っている環境を監視していること自体が噛み合わない    |
| 一時停止中は失敗扱いにしない     | 「DB に到達できない」を無視する死活監視は、何を確認しているのか分からない |
| キープアライブで一時停止を防ぐ   | 監視自体が7日間叩き続けても停止した。効かないことが実測で分かっている     |
| 有料プランに上げて常時起動にする | ポートフォリオの検証環境に継続課金する理由が無い（ADR 0005）              |
| ワークフローごと削除する         | プローブの中身はデプロイ後の確認に使える                                  |

## 影響

**一時停止した検証環境は、Supabase のダッシュボードから手で復帰させる。**
CLI に復帰用のコマンドは無い（`supabase projects` は list / create / delete のみ）。
復帰させないとデモにログインできず、`supabase db push` も通らない。

README がデモ環境を公開しているため、**眠ったままだと訪問者にはデモが
壊れているように見える**。ここは監視の問題ではなく運用の問題として別に扱う。

## 実装の落とし穴（0013 の実装から持ち越し）

**checkout しないジョブでは `gh` が対象リポジトリを決められない。**
`gh` はカレントディレクトリの git remote から対象を推測するため、
checkout の無いジョブでは `fatal: not a git repository` で全て失敗する
（`GH_REPO` を渡せば解決する）。

0013 のワークフローはこれを踏んでおり、`gh label create ... || echo 'label
already present'` の `||` が失敗を握り潰して**嘘の成功**を出していた。
ラベルは一度も作られておらず、本当に障害が起きても
`gh issue create --label` が落ちて**Issue は起票されなかった**。

今回 Issue の仕組みごと消したのでこのコードは残らないが、
**ジョブの成功は中のコマンドが成功したことを意味しない**という教訓は残す。
`||` で逃がすのは、逃がしてよい失敗だけに絞ること。
