# 0020. GET でのサインアウトを受け入れる（ログアウト CSRF は可用性のみの影響）

**状態**: 採用

## 背景

`/auth/signout`（`src/app/auth/signout/route.ts`）は **GET でサインアウトを実行する**。
状態を変える操作を GET で受けているため、第三者サイトのリンクや `<img>`、
トップレベル遷移から利用者を強制的にログアウトさせられる
（Supabase SSR の cookie は SameSite=Lax で、トップレベルの GET には付く）。
セキュリティ監査で指摘された（`security-audit-report.md` F-10、重要度: 低）。

利用者が自分で押すログアウト（ヘッダーのメニュー）は POST の Server Action
（`src/app/(auth)/actions.ts` の `signOut()`）で、このルートは使っていない。
このルートが GET なのには理由がある。メンバーシップを削除されたユーザーを
`getAuthContext()`（`src/lib/auth.ts`、RSC）から逃がす出口として使っている。

- RSC から `/login` へ直接リダイレクトすると、ミドルウェアが「認証済み」と見て
  ダッシュボードへ戻し、**リダイレクトループ**になる（Supabase の認証自体は生きている）
- cookie を消せるのは Route Handler と Server Action だけで、**RSC では消せない**
- RSC の `redirect()` が出せるのは GET の遷移だけ。POST の Route Handler や
  Server Action を RSC から起動する手段は無い

## 決定

**GET でのサインアウトをそのまま受け入れる。** 挙動は変えない。

## 理由

### 影響が可用性に限られる

強制ログアウトで起きるのは「もう一度ログインが必要になる」ことだけ。

- セッションを奪う・別アカウントでログインさせる（ログイン CSRF）ことはできない。
  このルートは cookie を消すだけで、新しいセッションを作らない
- データの変更・閲覧には至らない
- リダイレクト先は固定の `/login?reason=membership-revoked`。クエリを
  引き継がないので、オープンリダイレクトの足場にもならない

### 塞ぐと失うものの方が大きい

GET を確認画面にして POST で実行する案は、RSC からの出口として使えなくなる。
「メンバーシップを削除されたユーザーを確実に追い出す」という、こちらの方が
重いセキュリティ要件（除名の即時反映。ADR 0018）を壊すことになる。

## 捨てた案

| 案                                                                           | 却下理由                                                                                                   |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| GET では確認画面を出し、POST（Server Action）で実行する                      | RSC からの自動退出で利用者にボタンを押させることになり、押さなければ除名後もループ／滞留する               |
| GET を廃止する（利用者のログアウトは既に POST の Server Action `signOut()`） | RSC からの出口が無くなる。除名されたユーザーがリダイレクトループに入る                                     |
| GET に CSRF トークンを付ける                                                 | RSC の `redirect()` 先にトークンを載せる必要があり、トークンが URL・履歴・Referer に出る。得るものが小さい |
| `Sec-Fetch-Site` で同一オリジン以外を拒否する                                | 一部の経路（メールのリンク・ブックマーク）が `none` になり判定が揺れる。可用性の問題に複雑さを足すだけ     |

## 影響

- 第三者サイトから利用者を強制ログアウトさせることは引き続き可能。
  被害は再ログインの手間に限られる
- **このルートに「サインアウト以外の処理」を足さないこと。** 足した時点で
  GET で状態を変える経路の影響範囲が広がり、この判断の前提が崩れる。
  その場合はこの ADR を新しい ADR で上書きする
