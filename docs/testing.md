# テスト戦略

## 測定できるもの・できないもの

カバレッジの議論では C0 / C1 / C2 という段階がよく使われるが、
**JavaScript のツールで測れるのは C0 と C1 まで**である。

| 指標                  | 内容                             | 測定     | 本プロジェクトでの扱い |
| --------------------- | -------------------------------- | -------- | ---------------------- |
| C0（命令網羅）        | 各文が1回以上実行されたか        | 可       | `statements` / `lines` |
| C1（分岐網羅）        | 各分岐の真・偽を通ったか         | 可       | `branches`             |
| C2（条件網羅）・MC/DC | 複合条件の各項を個別に評価したか | **不可** | テスト設計で担保する   |

C2 が測れない以上、`a && b` のような複合条件は「両方の項をそれぞれ反転させたケースを書く」
という設計上の規律で担保するしかない。境界値も同様で、`max(5)` に対しては
**5（通る）と 6（弾かれる）の両方**を必ず書く。

### カバレッジが嘘をつく箇所

Zod スキーマのような宣言的なコードは、**モジュールを import しただけで
カバレッジ上 100% になる**。スキーマ定義は評価式であり、
実行されるのは「定義そのもの」だからである。

つまり `src/lib/validations/` の 100% は、
**検証ルールが機能していることを一切保証しない**。
ここは数値ではなく、境界値・不正形式・enum 外の値を明示的に通すテスト
（`tests/unit/validations-*.test.ts`）で担保している。

カバレッジは「テストが足りない場所を見つける道具」であって、
「テストが十分であることの証明」ではない。

## テストの層

| 層          | 対象                                                           | DB   | コマンド                |
| ----------- | -------------------------------------------------------------- | ---- | ----------------------- |
| unit        | Service Layer / Server Actions / Zod スキーマ / ユーティリティ | 不要 | `pnpm test:unit`        |
| integration | Supabase Auth の認証フロー                                     | 必要 | `pnpm test:integration` |
| rls         | RLS ポリシーによるテナント分離                                 | 必要 | `pnpm test:rls`         |
| e2e         | 画面操作                                                       | 必要 | `pnpm test:e2e`         |

CI では DB 不要な unit を先に回して早期に落とし、
DB / ブラウザを要する層は Supabase 起動後の別ジョブで実行する。

## カバレッジ計測

```bash
pnpm test:coverage
```

対象は `src/services/` `src/lib/` `src/app/**/actions.ts` に加え、
認証の配線である `src/app/auth/callback/route.ts` と `src/proxy.ts` に限定している。
UI コンポーネントや自動生成物まで含めると数値が薄まり、
本当に検証すべき認可・分岐が見えなくなるため。

`src/lib/supabase/` のうち Supabase クライアントの初期化（`client` / `server` /
`admin`）は薄いラッパなので除外しているが、`middleware.ts` だけは未認証
リダイレクトの判定を持つため計測対象に含める。`src/proxy.ts` はここへ
委譲しているだけで、判定そのものは `middleware.ts` 側にある。

閾値は `vitest.config.ts` の `coverage.thresholds` で定義しており、
下回ると CI が落ちる。**達成した水準は下げない**という回帰防止のための下限である。

## 共通ハーネス

| ファイル                         | 用途                                                        |
| -------------------------------- | ----------------------------------------------------------- |
| `tests/helpers/db-mock.ts`       | Drizzle のクエリビルダを模したチェーンモック                |
| `tests/helpers/auth-fixtures.ts` | ロール別 AuthContext と、ロール階層の境界を列挙するヘルパー |

`auth-fixtures.ts` の `rolesAtLeast(minRole)` / `rolesBelow(minRole)` は、
認可テストで「許可される最下位ロール」と「その1つ下」を機械的に網羅するためのもの。
成功する1ケースだけでは、権限チェックが実際に効いているかを確かめられない。

## 何を書くか

商用運用で問題になる経路を優先する。数値を上げるためだけのテストは書かない。

### Server Actions

Server Action は **未認証でも到達しうる公開 POST エンドポイント**であり、
UI を経由しない呼び出しが常に可能である。以下を全経路通す。

1. Zod 検証失敗 → エラーを返し、**Service Layer に到達しない**
2. 正常系 → Service に渡る引数（ctx と検証済みデータ）まで検証
3. `revalidatePath` は**成功時のみ**呼ばれる
4. `AuthorizationError` → 権限エラーへ変換
5. **それ以外の例外は握り潰さず再 throw する**

5 を怠ると、DB 障害が「理由不明の操作失敗」としてユーザーに見え、
監視にも上がらなくなる。

### Service Layer

- 認可の境界（許可される最下位ロールと、その1つ下）
- 全クエリに `org_id = ctx.orgId` が付くこと
- 書き込み系が監査ログを正しい action / resourceType / changes で残すこと

### コンポーネント（`.tsx`）

Server Component が既定のため、テストできるのは `'use client'` の付いた
クライアントコンポーネントに限られる。網羅は狙わず、次の順で優先する。

1. **認可の結果を画面に出すもの** — Service Layer は閲覧権限の無いフィールドを
   `null` にマスクし、権限外の一覧を空配列にして返す。受け手が落ちずに
   「—」や空状態へ落ちることは、サーバー側のテストでは分からない
2. **空状態・エラー表示** — 全画面に空状態と `error.tsx` を置く方針の回帰防止
3. **アクセシビリティ** — 名前・ラベル関連付け・キーボード到達性の回帰防止

### a11y の4本立て

| スペック                   | 見るもの                                                                    |
| -------------------------- | --------------------------------------------------------------------------- |
| `accessible-names.spec.ts` | 操作要素に名前があるか。**違反 HTML をそのまま出す**ので原因特定が速い      |
| `a11y-keyboard.spec.ts`    | キーボードで到達・操作できるか                                              |
| `a11y-axe.spec.ts`         | axe の標準ルール。**ダイアログを開いた状態**も見る                          |
| `a11y-contrast.spec.ts`    | light / dark 両方でコントラスト比。**ブラウザが解決した色**を canvas で測る |

axe と `accessible-names` は検出集合が一部重なるが、両方残している。
前者は標準ルールの網羅性、後者は失敗時のメッセージ品質が強み。

`a11y-contrast.spec.ts` は **axe の代わりではなく補完**。axe の
`color-contrast` はテキストしか見ないため、フォーカスリング（非テキスト・
SC 1.4.11）とグラフの系列色はこちらでしか担保できない。

**axe の除外は2つだけ。**

- `color-contrast` — 配色は今回のスコープ外（[ADR 0009](./adr/0009-form-a11y-wiring-lives-in-base-ui-field.md)）
- `.recharts-wrapper` — グラフの svg は装飾。同じ数値は統計カードとテーブルで別に提供している

`best-practice` タグは**入れない**。`withTags` でホワイトリストしているので、
上流の axe-core が新ルールを追加しても無関係な PR が落ちない。
**除外を増やすときは、なぜ増やすのかをスペック内のコメントに残すこと。**
検査が落ちたら検査ではなく実装を直す。

**フォームは全てダイアログ / シートの中にある。** 静的ページだけ検査しても
フォームは1つも見ていないことになるので、ダイアログを開いた状態の検査を
必ず維持すること。バリデーションエラー表示中の検査は、`.tsx` が
カバレッジ計測の対象外である以上、`FormField` の配線が生きていることを
実アプリで保証できる唯一の手段になっている。3. **フォームのバリデーション表示** — スキーマ自体は
`tests/unit/validations-*.test.ts` で担保済みなので、
**表示への配線**（失敗した入力が Server Action に届かないこと、
サーバー由来のエラーが toast に出ること）だけを見る 4. **条件分岐のあるテーブル/リスト表示** — ステータスのバッジ変換、
ページャの境界計算など

書かないもの:

- `src/components/ui/`（shadcn/ui の自動生成物。手動編集しない方針）
- スナップショット。変更検知にしかならず、壊れたことの説明にならない
- モックが実装より複雑になるもの（nuqs + debounce fetch を伴う一覧画面、
  Recharts、AI SDK のストリーミング、dnd-kit のセンサー）。
  これらは `tests/e2e/` の担当とする

`.tsx` は `vitest.config.ts` の `coverage.include` に**含めない**。
UI を数値目標にすると、意味の薄いレンダリングテストで閾値を埋める動機が生まれる。

補助:

| ファイル                              | 用途                                                            |
| ------------------------------------- | --------------------------------------------------------------- |
| `tests/setup.ts`                      | `afterEach(cleanup)` の登録（globals を使わないため明示が必要） |
| `tests/helpers/render-with-query.tsx` | TanStack Query 依存コンポーネント用の render                    |

### クライアント入力を信用しない検証

画面が送ってきた ID やロールをサーバーがそのまま使っていないか。
信用の起点（トークン、セッション）からサーバー側で引き直しているか。
`tests/unit/invite-actions.test.ts` の「トークン検証」ブロックがこの典型で、
クライアントが `role: 'owner'` を送っても招待レコードの値が使われることを検証している。

## テスト更新を強制するハーネス

プロダクトコードを変更したのにテストが置き去りになるのを防ぐため、
Claude Code のフックを `.claude/settings.json` に設定している。

| フック                                     | タイミング            | 役割                                                            |
| ------------------------------------------ | --------------------- | --------------------------------------------------------------- |
| `PostToolUse` (`Write`/`Edit`/`MultiEdit`) | `src/` を編集した直後 | 対応するテストファイルを**名指しで**提示する                    |
| `Stop`                                     | ターンを終える前      | `pnpm test:coverage` を実行し、失敗すれば完了を**ブロック**する |

## e2e のロール別セッション

`tests/e2e/global-setup.ts` は同一組織に **owner / member / viewer** の3ユーザーを
用意し、それぞれの `storageState` を `tests/e2e/.auth/` に保存する。
スペック側は `test.use({ storageState: AUTH_FILES.member })` でロールを選ぶ。

owner だけでログインしていた頃は、ロール別の認可（生年月日のマスク、
評価コメントのマスク、1on1 の当事者限定）が**画面まで効いているかを一切
検証できていなかった**。Service Layer のユニットテストは値がマスクされる
ことを保証するが、その値が実際に画面へ渡っていないことまでは示せない。

### マーカー文字列で検証する

判定には `E2E-SECRET-COMMENT-OTHERS` のようなマーカー文字列を使い、
**ページ全体のテキストに含まれないこと**を見る（`tests/e2e/authorization.spec.ts`）。
セレクタに依存しないため、表示箇所が変わってもマスク漏れを検出できる。
共有の定数は `tests/e2e/authorization-fixtures.ts` に置く
（Playwright はテストファイル同士の import を禁止しているため)。

### 対照群を必ず置く

「見えないこと」の検証は、**データが存在しないだけでも成立してしまう**。
そのため同じ値を owner では見えることを確認する対照群を必ず併記する。
これが無いとテストが素通りしていることに気付けない。

### 固定データ

`seedFixtures()` が service_role で直接投入する。同じ組織を使い回すため
すべて「存在しなければ作る」で書く。member 本人の従業員レコードには
`user_id` を入れること（入れないと本人判定が効かず、検証したい経路を通らない）。

viewer はあえて従業員レコードと紐付けていない。未紐付けのときに
「何も見えない」側へ倒れることの検証を兼ねている。

service_role で投入する処理は `tests/e2e/admin-api.ts` に置く。
Playwright はテストファイル同士の import を禁止しているため、
global-setup とスペックの両方から使うものは非スペックのモジュールに置く。

### コンポーネントテストから外したものの受け皿

「モックが実装より複雑になる」として `.tsx` 側で書かないと決めたものは、
e2e で実挙動を見る。何をもって「動いている」とするかは領域ごとに違う。

| 対象                    | スペック                       | 判定の置きどころ                                                             |
| ----------------------- | ------------------------------ | ---------------------------------------------------------------------------- |
| nuqs の URL 状態        | `employee-list-url-state.spec` | 操作 → URL に載る → リロードで復元される、の3点セット                        |
| Recharts                | `dashboard-charts.spec`        | svg の存在だけでなく**系列が0本でないこと**                                  |
| dnd-kit                 | `department-dnd.spec`          | ドロップ後に**リロードして永続化**（画面だけ動いて DB に入らない回帰を防ぐ） |
| AI SDK のストリーミング | `ai-assistant.spec`            | デモモードの固定応答が**画面に出る**ところまで                               |

補足:

- debounce を挟む操作は固定待機ではなく `waitForURL` で待つ
- 件数を数えるテストは、専用データを投入して検索で母集団を固定する。
  組織全体の件数に依存させると他スペックの実行順序で壊れる
- Recharts と dnd-kit は「何も起きていない」状態でも通ってしまう判定に
  なりやすい。前者は系列の本数、後者はドロップ前に `isDragging` を
  確かめてから離すことで、素通りを防いでいる
- 空状態の対照群は**データを持たない別組織**を作って取る。
  同じ組織では「データがある」と「無い」を同時に用意できない

### 対応表（`.claude/hooks/test-reminder.sh`）

| 編集したファイル           | 提示されるテスト                      |
| -------------------------- | ------------------------------------- |
| `src/services/<name>.ts`   | `tests/unit/<name>-service.test.ts`   |
| `src/app/**/actions.ts`    | `tests/unit/<domain>-actions.test.ts` |
| `src/lib/validations/*.ts` | `tests/unit/validations-*.test.ts`    |
| `src/lib/<name>.ts`        | `tests/unit/lib-<name>.test.ts`       |
| `src/app/**/page.tsx`      | `tests/e2e/<screen>.spec.ts`          |

「テストも書くこと」という一般論ではなく、更新すべきファイル名と
そのレイヤ固有の観点まで出す。既存かどうかも区別して伝える。

### なぜ Stop フックが必要か

`PostToolUse` の提示は気づきを与えるだけで、無視できてしまう。
実際の担保は `Stop` フックが行う。

実行するのは DB 不要な unit + カバレッジのみ（約15秒）。
`rls` / `integration` / `e2e` はローカル Supabase の起動が前提で、
起動していない環境で毎回落ちると単なる邪魔になるため CI に任せている。

`src/` と `tests/` に未コミットの変更が無ければ即座に終了するため、
調査だけのターンでは走らない。

### 有効化

`.claude/` を新規作成した直後のセッションでは、設定ウォッチャーが
このディレクトリを監視しておらずフックが読み込まれない。
`/hooks` を一度開くか、セッションを再起動すると反映される。
